# DevOps Best-Practices Checklist

Use this as an **assessment**, not a to-do list. Score honestly, find the lowest-scoring
section, and start there. Anything you cannot answer is itself a finding.

---

## 1 · Source control
- [ ] Every artefact — code, pipelines, infra, manifests, dashboards, alerts, policy — is in git
- [ ] `main` is protected: no direct pushes, no force-push, no deletion
- [ ] Every change goes through a reviewed pull request
- [ ] CI status checks are **required** before merge
- [ ] Branches live **under 24 hours**; PRs are under ~400 lines changed
- [ ] Merged branches are deleted automatically
- [ ] `CODEOWNERS` routes review, and **covers `.github/workflows/` and deployment paths**
- [ ] Commit messages follow a convention and explain **why**
- [ ] `.gitignore` excludes secrets, state files and build artefacts
- [ ] No secret has ever been committed (verified by a history scan, not by memory)

## 2 · Continuous integration
- [ ] Every push and PR triggers an automated build
- [ ] The build is **self-testing** — a green build means something
- [ ] Pipeline completes in **under 10 minutes**
- [ ] A red mainline is a **stop-the-line** event, fixed before new work
- [ ] The build state is visible to everyone
- [ ] Tests follow the pyramid: mostly fast unit tests
- [ ] Flaky tests are **fixed or deleted**, never re-run as a coping mechanism
- [ ] The artefact is built **once** and promoted unchanged
- [ ] Dependencies are pinned; a lock file is committed
- [ ] Third-party CI Actions/plugins are **pinned to a SHA**, not a tag

## 3 · Containers
- [ ] Multi-stage builds; no compilers or build tooling in the shipped image
- [ ] Base images pinned by digest, and **rebuilt regularly** for CVE patches
- [ ] Containers run as a **non-root, numeric UID**
- [ ] Read-only root filesystem; all capabilities dropped
- [ ] Resource requests **and** limits set on every workload
- [ ] `.dockerignore` present
- [ ] Exec-form `CMD`/`ENTRYPOINT`; `SIGTERM` handled gracefully
- [ ] Logs go to stdout/stderr as structured JSON
- [ ] Images tagged with the **commit SHA**; no `:latest` in any deployment manifest
- [ ] OCI labels tie the image back to its source commit
- [ ] Every image is scanned in CI, and the scan is a **gate**

## 4 · Kubernetes
- [ ] Liveness probe has **no external dependencies**; readiness probe checks them
- [ ] `maxUnavailable: 0` (or equivalent) for zero-downtime rollouts
- [ ] PodDisruptionBudget on every user-facing service
- [ ] Configuration externalised; **one image per environment set**
- [ ] Secrets are not plaintext in git (Sealed Secrets / SOPS / External Secrets / Vault)
- [ ] Encryption at rest enabled for etcd
- [ ] NetworkPolicy: default-deny, with explicit allows
- [ ] Namespaces have ResourceQuota and LimitRange
- [ ] Pod Security Admission enforced
- [ ] `automountServiceAccountToken: false` unless the pod needs API access
- [ ] Admission policy (Kyverno/OPA) rejects non-compliant workloads
- [ ] Stateful workloads use StatefulSets with PVCs, and **restores are tested**

## 5 · Infrastructure as Code
- [ ] All infrastructure is defined in code; **no ClickOps**
- [ ] State is remote, encrypted **and locked**
- [ ] `plan` runs on every PR and is reviewed by a human
- [ ] `apply` runs only from CI, never from a laptop
- [ ] Providers, modules and versions are pinned; lock files committed
- [ ] Drift detection runs on a schedule and alerts on a non-empty plan
- [ ] `prevent_destroy` on databases and other irreplaceable resources
- [ ] Environments are the same modules with different variables
- [ ] IaC is scanned for misconfiguration in CI
- [ ] Configuration management is idempotent (`changed=0` on a second run)

## 6 · Continuous delivery
- [ ] Deployment is fully automated and identical across environments
- [ ] The same artefact is promoted; nothing is rebuilt per environment
- [ ] **Rollback is one command and has been tested this quarter**
- [ ] Deployment strategy is deliberate (rolling / blue-green / canary), not accidental
- [ ] Deploy and release are separable (feature flags)
- [ ] Database changes use expand/contract and are decoupled from code deploys
- [ ] Smoke tests run automatically after every deployment
- [ ] Failed deployments roll back **automatically**
- [ ] The change record is generated by the pipeline, not typed by a human
- [ ] There are no change freezes (or you can defend why there are)

## 7 · Security (DevSecOps)
- [ ] Secret scanning on every commit **and across full history**
- [ ] SAST in the pipeline, gating on high severity
- [ ] SCA (dependency scanning) gating on fixable vulnerabilities
- [ ] Container image scanning gating on fixable HIGH/CRITICAL
- [ ] IaC misconfiguration scanning
- [ ] **SBOM generated per build, stored, and re-scanned** as new CVEs appear
- [ ] Exceptions have an **owner and an expiry date**, reviewed at release
- [ ] No long-lived credentials in CI — OIDC federation or short-lived tokens
- [ ] Pipeline permissions are least-privilege
- [ ] Images are signed and verified at admission
- [ ] There is a **written, rehearsed** procedure for a leaked credential (rotate first)

## 8 · Observability
- [ ] Every service exposes metrics, structured logs and (ideally) traces
- [ ] A correlation/trace ID ties logs to requests across services
- [ ] RED metrics for services; USE metrics for resources
- [ ] Dashboards are **code**, in git, not clicked together in a UI
- [ ] SLIs and SLOs are defined **from user need**, with an error budget
- [ ] Alerts fire on **symptoms**, not causes
- [ ] Every alert is actionable and links to a runbook
- [ ] Multi-window burn-rate alerting rather than raw thresholds
- [ ] Alerts are reviewed monthly; non-actionable ones are deleted
- [ ] No secrets or PII in logs
- [ ] Log retention is tiered and costed

## 9 · Incident management
- [ ] Severity levels are defined **in advance**
- [ ] On-call rota is explicit, humane and fairly compensated
- [ ] Incident Commander role is assigned during incidents, and does not debug
- [ ] Mitigation comes **before** root-cause analysis
- [ ] Every significant incident gets a **blameless** post-mortem within 48 hours
- [ ] Post-mortems produce owned, dated action items that are actually tracked
- [ ] Post-mortems are published organisation-wide
- [ ] Runbooks exist, are linked from alerts, and are tested in game days

## 10 · Culture and measurement
- [ ] The four DORA metrics are measured, trended, and **not used to rank teams**
- [ ] Speed and stability are reported **together**
- [ ] Teams own their services in production ("you build it, you run it")
- [ ] Improvement work is budgeted (e.g. 20 % of capacity), not "when we get time"
- [ ] Toil is measured and actively reduced
- [ ] Post-incident questions ask "what made this possible?", never "who did it?"
- [ ] WIP is limited and work is visible
- [ ] Knowledge, tools and runbooks are shared across teams
- [ ] The compliant path is also the **easiest** path

## The ten anti-patterns — do you have them?

| Anti-pattern | Present? | First step |
|---|---|---|
| DevOps team as a third silo | | Stream-aligned teams + a platform team |
| DevOps = buying tools | | Change the metrics and the incentives |
| Automating a broken process | | Map the value stream first |
| Vanity metrics (deploys up, incidents up) | | Always pair speed with stability |
| No tested rollback | | Rehearse one this week |
| Manual, undocumented deploys | | Automate; remove the single point of knowledge |
| Snowflake environments | | IaC + immutable infrastructure |
| Security bolted on at the end | | Shift left; gate on real risk |
| Alert fatigue | | Delete every non-actionable alert |
| Long-lived branches | | Trunk-based + feature flags |
